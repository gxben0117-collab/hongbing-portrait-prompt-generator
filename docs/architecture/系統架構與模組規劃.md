# 系統架構與模組規劃

## 現況架構

目前專案採用：

- `index.html`
  - UI 結構
  - 全量 `CATS` 風格資料
  - 啟動狀態與初始化
- `core.js`
  - 核心咒語邏輯
  - 模板、選項、渲染、狀態切換
  - prompt 組裝與輸出

這種架構可以快速迭代，但已有明顯耦合：

1. UI 與資料耦合
2. 資料與生成邏輯耦合
3. 建置與發佈邊界不清楚
4. 文件與實際工程角色沒有完全對齊

## 目標工程結構

在保留現行 `index.html + core.js` 相容前提下，逐步演進到：

```text
root
├─ index.html                # 相容入口
├─ core.js                   # 相容核心入口
├─ dist/                     # 發佈產物
├─ scripts/                  # 工程腳本
├─ docs/                     # 文件中心
├─ 核心資料/                 # 規範與來源資料
└─ src/                      # 後續逐步導入的模組層
   ├─ data/
   ├─ prompt/
   ├─ ui/
   ├─ state/
   └─ render/
```

## 模組規劃

### 1. data

責任：

- 風格分類資料
- 場景條目資料
- 妝容、鏡頭、燈光、氛圍等結構化設定

目標：

- 把目前散落在 `index.html` / `core.js` 的資料層逐步明確化

### 2. prompt

責任：

- 核心 prompt 組裝
- 姿勢誘導
- 規則拼接

限制：

- `核心資料/核心咒語規範.md` 為權威來源，未獲使用者同意不得更動

### 3. state

責任：

- 當前分類、條目、鏡頭、比例、妝容等 UI 狀態

### 4. render / ui

責任：

- 畫面渲染
- 按鈕、切換、輸出區等互動

## 相容策略

短期不直接推翻現有結構。

先做：

1. 文件治理
2. 腳本治理
3. 邊界治理
4. 低風險抽離

再逐步把大型資料與渲染責任拆開。
