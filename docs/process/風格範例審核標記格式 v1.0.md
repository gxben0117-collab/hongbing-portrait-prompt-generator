# 風格範例審核標記格式 v1.0

日期：2026-05-22

## 目的

這份文件定義未來對 `風格範例.md`、候選卡片草稿與 runtime 前審結果的正式標記格式。

重點不是先改成某種資料庫，而是先把「審核結果要怎麼表示」統一，避免不同 AI 用不同說法。

## 使用場景

適用於以下工作：

- 新增風格卡前的人工作業
- AI 自動補庫後的人工複核
- `legacy` 舊資料盤點
- `approved / review / blocked` 的前審結果保存
- 後續 lint 腳本輸出格式設計

## 核心原則

標記格式必須滿足：

1. 人類可讀
2. AI 可穩定產生
3. 之後容易轉成 JSON / YAML / TSV / 腳本輸出
4. 不要求立刻改動現有 runtime

## 最小標記欄位

每張卡的審核標記，至少應包含以下欄位：

- `id`
- `name`
- `category_id`
- `tpl`
- `source_type`
- `status`
- `risk_flags`
- `review_notes`
- `last_reviewed_at`
- `reviewed_by`

## 欄位定義

### `id`

- 對應風格卡唯一識別碼
- 若來源是 md 草稿，尚未正式編號，也應先給臨時 id

### `name`

- 卡片主名稱

### `category_id`

- 對應 runtime 分類 id
- 例如：
  - `song_grace`
  - `queen`
  - `wedding_diamond`

### `tpl`

- 對應模板類型
- 例如：
  - `hanfu`
  - `queen`
  - `wedding`
  - `reference_styles`

### `source_type`

允許值：

- `manual`
  - 人工原創整理

- `curated`
  - 人工策展或人工重寫後通過

- `auto`
  - AI 或腳本批量生成

- `legacy`
  - 舊世代歷史資料

### `status`

允許值：

- `approved`
- `review`
- `blocked`
- `legacy`

定義：

- `approved`
  - 已符合核心規範與 runtime 前審要求

- `review`
  - 有可用價值，但仍需人工調整

- `blocked`
  - 含重大高風險內容，不可進主流程

- `legacy`
  - 保留歷史參考，但不可默認視為安全資料

### `risk_flags`

建議為陣列概念，允許多值：

- `identity_risk`
- `beauty_risk`
- `pose_risk`
- `camera_risk`
- `fx_risk`
- `mapping_gap`
- `duplication_risk`
- `legacy_style_drift`

若無風險，可填空陣列概念或 `none`。

### `review_notes`

- 人工或 AI 的審核備注
- 需簡短、具體、可執行

例如：

- `角色氛圍含 heroine，需改為中性世界觀描述`
- `構圖主打人物極小，與 face readability 主線衝突`
- `可保留題材，但需重寫 prop / comp`

### `last_reviewed_at`

- 使用固定日期格式
- 建議：`YYYY-MM-DD`

### `reviewed_by`

- 記錄執行者
- 可填：
  - `Codex`
  - `Claude`
  - `User`
  - `Manual`

## 建議標記格式

### 方案 A：Markdown 區塊格式

適合先人工使用。

範例：

```md
### review: v624_xianxia_01
- id: v624_xianxia_01
- name: 蓮台渡劫聖女 · 城樓守望
- category_id: xianxia
- tpl: xianxia
- source_type: legacy
- status: review
- risk_flags: [identity_risk, beauty_risk]
- review_notes: 角色氛圍含 heroine，需改寫成中性世界觀語句後再進 runtime
- last_reviewed_at: 2026-05-22
- reviewed_by: Codex
```

### 方案 B：TSV / CSV 欄位格式

適合後續批量盤點。

欄位順序建議：

`id | name | category_id | tpl | source_type | status | risk_flags | review_notes | last_reviewed_at | reviewed_by`

### 方案 C：JSON 輸出格式

適合未來 lint 腳本。

範例：

```json
{
  "id": "v624_xianxia_01",
  "name": "蓮台渡劫聖女 · 城樓守望",
  "category_id": "xianxia",
  "tpl": "xianxia",
  "source_type": "legacy",
  "status": "review",
  "risk_flags": ["identity_risk", "beauty_risk"],
  "review_notes": "角色氛圍含 heroine，需改寫成中性世界觀語句後再進 runtime",
  "last_reviewed_at": "2026-05-22",
  "reviewed_by": "Codex"
}
```

## 當前建議

在還沒正式做腳本前，建議先採用：

- Markdown 作為人工對話與 AI 中介格式
- JSON 作為未來腳本目標格式

也就是：

先用 md 寫審核結果，之後再轉成結構化輸出。

## 標記使用規則

1. `legacy` 不等於 `blocked`
   - `legacy` 是歷史資料身份
   - `blocked` 是目前不可進 runtime 的判定

2. `review` 必須附 `review_notes`
   - 不能只說要 review，必須說明為什麼

3. `approved` 也可帶輕度風險標記
   - 例如已重寫後可用，但仍保留 `duplication_risk`

4. `risk_flags` 應用於原因標記，不直接等於最終結論

## 與現有文件的關係

本文件回答的是：

- 審核結果要怎麼寫

不是：

- 什麼叫高風險
- 什麼叫資料結構
- 什麼叫核心規範

對應關係如下：

- `風格範例資料結構規格 v1.0`
  - 定義資料長相

- `風格範例 lint 與審核規則 v1.0`
  - 定義怎麼判定風險

- 本文件
  - 定義判定結果怎麼標記

## 最終原則

先把審核標記格式統一，後面的腳本、自動盤點、legacy 分流、approved 清單，才會有共同語言。
